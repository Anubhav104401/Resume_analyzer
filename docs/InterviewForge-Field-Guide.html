Section 1

What this project actually is

Before a single line of code makes sense, you need the one-paragraph version of what you own.

InterviewForge AI is a website that only runs on your own computer. You start it by typing one command in a terminal. That command opens a page in your browser at an address like http://localhost:8501. Nobody else on the internet can see it unless you deliberately publish it somewhere.

What the website does, start to finish:

  1. You drag a resume file (PDF or Word) into a box on the left.
  2. You type the job you want — "Data Scientist", "Frontend Developer" — and pick how experienced you are from a dropdown.
  3. You click one button: 🚀 Generate AI Analysis.
  4. The program pulls the plain words out of your file (a PDF is not text — it's a container that holds text, and something has to dig it out).
  5. It then sends those words to Google Gemini — an AI model running on Google's computers, not yours — four separate times, asking four different questions.
  6. It takes the four answers and paints them into a dashboard with four tabs: a score with a radar chart, a resume critique, forty interview questions, and a 90-day study plan.
The single most important idea

This project contains no artificial intelligence of its own. There is no machine learning model in your folder, nothing was trained, no algorithm "learns". All the intelligence lives on Google's servers and is rented, one question at a time, over the internet. Your code's real job is: read a file → write a good question → send it → catch the answer → arrange the answer prettily on screen. That is genuinely all of it, and understanding that removes about 80% of the mystery.

What it is not

  • Not a database app. Nothing is saved. Refresh the browser and your analysis is gone forever.
  • Not a multi-user product. There are no accounts, no logins, no separation between people. One person, one laptop, one API key.
  • Not a frontend + backend pair. There is no React app talking to a Python server. There is one Python script; a tool called Streamlit turns it into both the page and the server at the same time. This surprises people, and it's the key to why the code looks the way it does.
  • Not trained on your data. Your resume text is sent to Google's API and used to produce an answer; the app itself stores nothing.

Section 2

The absolute basics

Every term used in the rest of this guide, defined here first, with no jargon leaning on other jargon. Skip anything you already know.

Files, folders, and what "running" means

A file ending in .py is a plain text file full of Python instructions. Nothing about it is magic — you could open app.py in Notepad. "Running" it means handing that text file to a program called the Python interpreter, which reads your instructions top to bottom, one line at a time, and does what each one says. When it reaches the bottom, it stops.

A folder (also called a directory) is just a container. In this project the folders group code by job: services/ holds code that does work, utils/ holds tiny reusable helpers, assets/ holds non-code files like the stylesheet.

Variables

A variable is a labelled box you put a value in so you can use it later.

examplepython
target_role = "Data Scientist"     # a box named target_role, holding text
experience_level = "Fresher"       # another box

In your project, target_role in app.py line 55 is exactly this: a box that holds whatever the user typed into the text field.

Strings, lists, dictionaries

  • String — text in quotes: "Data Scientist". Any text at all, including a whole resume.
  • List — an ordered collection in square brackets: ["Student", "Fresher", "Intern"]. Your experience-level dropdown is literally a list (line 60 of app.py).
  • Dictionary — pairs of key → value in curly braces: {"overall": 85, "technical_skills": 80}. You look things up by name rather than by position: scores["overall"] gives you 85. This is the single most important data shape in this whole project, because it is the same shape as JSON (more on that in a moment).

Functions

A function is a named recipe. You define it once, then "call" it as many times as you like. Values you hand in are arguments; the value it hands back is what it returns.

examplepython
def greet(name):            # define a recipe called "greet" that takes one ingredient
    return "Hello " + name  # hand back a new piece of text

message = greet("Anubhav")  # call it; message now holds "Hello Anubhav"

Note the indentation. Python does not use braces to show what's "inside" something — it uses indentation, usually four spaces. Everything indented under def greet(name): belongs to that function. Get the indentation wrong and the program genuinely means something different. This is Python's most famous quirk.

Classes and objects

A class is a blueprint. An object is one thing built from that blueprint. GeminiClient in gemini_service.py is a blueprint describing "something that knows how to talk to Google's AI". The line client = GeminiClient() builds one actual talker from that blueprint and puts it in a box called client.

Inside a class, self means "this particular object". self.client means "the client belonging to this GeminiClient", not some other one. And __init__ is the special recipe that runs automatically at the moment an object is built — the setup routine.

Imports and libraries

Nobody writes everything from scratch. A library (or package) is code someone else wrote and published; you install it and use it. import is how you pull it in.

app.py lines 1–10python
import streamlit as st                        # pull in Streamlit, nickname it "st"
from services.resume_parser import ResumeParser  # pull ONE thing out of one of your files

import x as y means "import x but let me call it y" — everyone nicknames Streamlit st because it's typed hundreds of times. from a.b import C means "reach into folder a, file b, and grab just C".

pip, requirements.txt, and virtual environments

pip is Python's installer. pip install streamlit downloads Streamlit onto your machine. requirements.txt is a shopping list so that anyone (including future you on a new laptop) can install everything in one command: pip install -r requirements.txt.

A virtual environment (a venv folder) is a private toolbox for one project, so Project A can use Streamlit 1.30 while Project B uses 1.42 without them fighting. Your project has none right now — the libraries are installed globally on your machine. That works fine for a solo project; it only becomes a problem when two projects want different versions of the same library.

JSON — the single most important format here

JSON stands for JavaScript Object Notation. Forget the name. It is a way of writing structured data as plain text so two different programs — possibly written in different languages, running on different continents — can agree on what the data means.

what JSON looks likejson
{
  "summary": "Strong Python fundamentals, thin on deployment experience.",
  "strengths": ["Clean project structure", "Good SQL depth"],
  "scores": { "overall": 72, "technical_skills": 68 }
}

Rules: curly braces make an object (key → value pairs), square brackets make a list, keys are always in double quotes, text values are in double quotes, numbers are bare. That's basically it.

Why this matters so much

A Python dictionary and a JSON object are the same idea in two costumes. json.loads(text) reads JSON text and hands you a Python dictionary. That one function is the bridge between "the AI sent me some characters" and "I have real data I can display". Everything in section 7 is about that bridge.

APIs and HTTP requests

An API is a doorway one program opens so other programs can ask it for things. Google runs an API for Gemini. Your program walks up to that doorway, hands over a written question plus a key proving you're allowed to ask, and receives a written answer.

The delivery mechanism is HTTPS — the same protocol your browser uses. A request goes out (containing your prompt, encoded as JSON), a response comes back (containing the AI's answer, also JSON). "S" means encrypted in transit, so nobody between you and Google can read your resume text.

Environment variables and .env

Your Gemini API key is a password. If you typed it directly into gemini_service.py and pushed that to GitHub, a bot would find it within minutes and spend your quota. So instead the key lives in a separate file named .env, which .gitignore tells Git to never upload. At startup, load_dotenv() reads that file and loads the key into the program's memory, where os.getenv("GEMINI_API_KEY") can fetch it.

try / except — how Python survives mistakes

Some operations can fail: a PDF might be corrupt, the internet might drop, Google might be overloaded. try: means "attempt this". except Exception as e: means "if it blew up, don't crash the whole program — run this instead, and put the error object in a box called e". raise means "deliberately throw an error upward for someone else to catch". Your project uses this pattern in every single service file.

Decorators

A line starting with @ directly above a function is a decorator — a wrapper that changes how that function behaves without editing its insides. @st.cache_resource above get_services() in app.py means "run this once and remember the result; on later runs, hand back the same thing instead of doing the work again."

f-strings

A string with an f in front lets you drop variables straight into the text using curly braces: f"Targeting: {target_role}" becomes "Targeting: Data Scientist". Every AI prompt in this project is built with a multi-line f-string. One gotcha you'll see in analyzer.py: because { already means "insert a variable", writing a literal curly brace inside an f-string requires doubling it — {{ and }}. That's why the JSON examples inside those prompts look strangely doubled.

The same thing as a numbered story

  1. You run streamlit run app.py. Streamlit starts a small web server on your machine, listening on port 8501, and opens your browser to it.
  2. Streamlit executes app.py top to bottom. Every st.something() call it meets adds an element to the page description it's building. When it finishes, it ships that description to the browser.
  3. You upload a resume. The browser sends the raw bytes up to the Streamlit server, which holds them in memory as an object (see section 6).
  4. You type a role, pick a level, click the button. Each of those interactions makes Streamlit re-run the entire script from line 1. This is the single strangest thing about Streamlit and it explains almost every design choice in app.py.
  5. On the run where the button was clicked, the variable analyze_btn is True, so execution enters the if analyze_btn: block on line 70.
  6. Guard checks run first (lines 71–76): no file? no role? services broken? Each shows a red error and stops there.
  7. Text extraction (line 80): ResumeParser.extract_text() opens the in-memory file, detects PDF vs DOCX from the filename, and returns one long string of every word in your resume.
  8. AI call #1 — analysis (line 86): builds a prompt containing your resume text, the target role, and the level; asks for strengths, weaknesses, missing skills, recruiter feedback.
  9. AI call #2 — scoring (line 89): a separate prompt asking for five numbers 0–100 plus improvement suggestions.
  10. AI call #3 — interview questions (line 93): asks for 10 questions in each of 4 categories.
  11. AI call #4 — roadmap (line 96): takes the missing skills list produced by call #1 and asks for a 30/60/90-day plan to close those gaps. This is the only call that depends on a previous call's output.
  12. Each reply is rescued into a Python dictionary by extract_json_from_text().
  13. The four dictionaries are stored in st.session_state (lines 100–103) so they survive all future re-runs.
  14. The script continues to line 109, sees that 'analysis' now exists in session state, and draws the four-tab dashboard. Every tab switch after that re-runs the whole script again — but now the data is already in memory, so no AI calls happen and it feels instant.
Why Streamlit re-runs everything

In a normal website, JavaScript changes small pieces of the page in place. Streamlit deliberately threw that model away: instead of tracking what changed, it just runs your whole script again and diffs the result. That's why the code reads like a simple top-to-bottom script with no event handlers or callbacks anywhere. The price you pay is that any variable not stored in st.session_state is wiped and rebuilt on every single interaction — including expensive things like AI results. That's the entire reason lines 100–103 exist.

A quirk worth knowing about

Look carefully at lines 86–97. Each progress_bar.progress(N, text=...) fires after a step finishes, but its label describes the step that's about to start. So when the bar reads "Generating Readiness Score" at 25%, the analysis has just completed and the score request hasn't been sent yet. It's forward-looking rather than backward-looking. Not a bug — but if you ever wonder why the last label ("Analysis Complete!") appears while a spinner is still spinning, that's why.

How long does it take?

Four sequential requests, each typically 3–10 seconds of Gemini thinking time, plus a hard-coded minimum 3-second gap between calls (CALL_SPACING), plus PDF parsing. Realistically 20–50 seconds per full run. Nothing runs in parallel — see section 10 for why that was a reasonable choice and what it would take to change.

Ports, servers, and the "middleware" question

You asked what port the middleware listens on and how the JSON request reaches it. The honest answer reshapes how you should picture this app — so here it is in full.

There is no middleware in this project

"Middleware" usually means a layer sitting between a frontend and a backend — an Express server, a Flask API, an nginx proxy. This project has none of that. There is exactly one program: the Python process started by streamlit run app.py. It is simultaneously the web server, the UI renderer, and the business logic. Nothing you wrote listens for incoming API requests.

What the outbound JSON actually looks like

You never write this JSON by hand. When gemini_service.py calls self.client.models.generate_content(model=..., contents=prompt, config=...), the Google SDK converts those Python arguments into an HTTPS request whose body is roughly this shape:

And the reply that comes back is JSON too — with the model's actual answer buried inside it as a string. The SDK unwraps that for you and hands your code just the string, which is what response.text is on line 84 of gemini_service.py.

The mental correction

The JSON in this project is not traffic between your frontend and your backend — you don't have those as separate pieces. The JSON is traffic between your one program and Google. Your entire codebase sits on the client side of that relationship.

Could someone else on your Wi-Fi open the app?

By default Streamlit binds to your machine and prints both a Local URL and a Network URL. If you use the network URL, other devices on the same Wi-Fi can reach it — and they would be spending your API key with no login in the way. For a tool with no authentication, treat it as a localhost-only app unless you deliberately add auth first.

Section 6

The file upload system, in forensic detail

You asked for every minute detail of the resume upload box. It is produced by a single line of Python — but that line hides a five-stage journey. Here is all of it.

The line that creates it

app.py line 52python
uploaded_file = st.file_uploader("Upload PDF or DOCX", type=['pdf', 'docx'])

That's the whole upload system as far as your code is concerned. Three pieces:

  • "Upload PDF or DOCX" — the label printed above the box. Change this string to change that text.
  • type=['pdf', 'docx'] — the allowed extensions. This does two things: it sets the accept attribute on the underlying HTML file input (so the operating system's file picker greys out other files), and it makes Streamlit reject a mismatched file with its own red error before your code ever sees it.
  • uploaded_file = — the box that catches the result. It holds None when nothing is uploaded, and an UploadedFile object once something is.

Stage 1 — the browser side

Streamlit renders a drag-and-drop panel containing a hidden standard HTML <input type="file">. Clicking "Browse files" opens your operating system's native file dialog. Dropping a file onto the panel uses the browser's drag-and-drop API. Either way the browser ends up holding a File object — a handle to bytes sitting on your disk.

The visible caption "Limit 200MB per file • PDF, DOCX" is generated by Streamlit from two sources: the type list you passed, and the server.maxUploadSize config value, which defaults to 200 (megabytes) because your project has no config file overriding it.

Stage 2 — bytes travel to the server

Streamlit's JavaScript uploads the raw bytes to the Python process over a separate background HTTP POST — not over the WebSocket that carries normal UI updates. The upload is tagged with the session ID and a unique file ID so the server knows which browser tab and which widget it belongs to. A progress indicator appears for large files. This entire exchange is internal Streamlit machinery; there is no code in your project involved, and no endpoint you can call yourself.

Stage 3 — the UploadedFile object

Once the bytes arrive, Streamlit re-runs your script, and this time uploaded_file holds an UploadedFile object. Two facts about it matter enormously:

  • It lives in RAM, not on disk. Technically it subclasses io.BytesIO — a chunk of memory that pretends to be a file. Your resume is never written to your hard drive by this app. When the session ends, it evaporates.
  • It behaves exactly like an opened file. It supports .read(), .seek(), and iteration. That's why PyPDF2 and python-docx accept it directly without complaining — they can't tell the difference between this and a real file handle.

It also carries metadata: .name (the original filename, used on line 80 to decide PDF vs DOCX), .size (bytes), and .type (the MIME type the browser guessed).

Stage 4 — extension detection

services/resume_parser.py lines 17–25python
ext = filename.split('.')[-1].lower()

if ext == 'pdf':
    return ResumeParser._extract_from_pdf(file_obj)
elif ext in ['doc', 'docx']:
    return ResumeParser._extract_from_docx(file_obj)
else:
    raise ValueError(f"Unsupported file format: {ext}. Please upload PDF or DOCX.")

Read filename.split('.')[-1].lower() right to left: split('.') chops "Anubhav_Resume.final.pdf" into ["Anubhav_Resume", "final", "pdf"]; [-1] takes the last piece (negative indexing counts from the end); .lower() makes "PDF" and "pdf" identical. Robust against multiple dots and any capitalisation.

Two real weaknesses here

1. 'doc' is accepted in the elif branch, but old-style .doc files are a completely different binary format that python-docx cannot read. If a .doc ever got through, it would fail with a confusing parsing error. (Streamlit's own type=['pdf','docx'] filter blocks it first, so this branch is currently unreachable — but it's a trap waiting for anyone who widens that list.)

2. Validation looks at the filename only, never the file's contents. Rename notes.txt to notes.pdf and the code will happily hand it to PyPDF2, which throws a raw low-level error. Proper validation would check the first few bytes — every real PDF starts with the characters %PDF.

Stage 5 — text extraction

For PDFs, PyPDF2 opens the in-memory buffer, loops over every page, and calls page.extract_text(), gluing the results together with newlines. For DOCX, python-docx loads the document and walks doc.paragraphs, appending each paragraph's text.

The big limitation nobody warns you about

PDFs come in two flavours. A PDF exported from Word or LaTeX contains a real text layer — extraction works perfectly. A PDF that is a scan or photo of a page contains only an image; there is no text to extract, and extract_text() returns empty strings for every page. Your code catches this on line 41–42 and raises "PDF appears to be empty or contains only unextractable images." Reading image-based PDFs would require OCR (optical character recognition, e.g. Tesseract) — a much heavier dependency this project deliberately does not carry.

Similarly, python-docx reads only doc.paragraphs. Text inside tables, headers, footers or text boxes is silently skipped. Many resume templates put contact details or skills in tables — so a table-heavy DOCX may lose real content without any error.

What the AI eventually receives

Every bit of formatting is gone. Fonts, columns, bullets, colours, spacing — none of it survives. The AI sees one long plain string, roughly:

what resume_text looks liketext
ANUBHAV KUMAR
anubhav@example.com | +91 90000 00000 | github.com/anubhav
EDUCATION
B.Tech Computer Science, 2022-2026, CGPA 8.4
SKILLS
Python, SQL, Pandas, Streamlit, Git
PROJECTS

This has a practical consequence: when the AI comments on "resume quality", it is judging wording and content, and cannot see your layout, your font choices, or whether it fits on one page. It's guessing about visual quality from text alone.

Section 7

Turning plain text into JSON

You asked what algorithm converts plain text into a JSON that satisfies the required format. There are three distinct mechanisms stacked on top of each other, and only one of them is code you own.

Mechanism 1 — showing the AI the shape you want (prompt engineering)

The "conversion" starts before anything is sent. Your prompt literally contains a drawing of the JSON you want back:

services/analyzer.py lines 17–25python
Provide your response in JSON format exactly matching this structure:
{{
    "summary": "A 3-4 sentence professional summary of the candidate's fit.",
    "strengths": ["Strength 1", "Strength 2", "Strength 3"],
    "weaknesses": ["Weakness 1", "Weakness 2"],
    "missing_skills": ["Skill 1", "Skill 2", "Skill 3"],
    "recruiter_feedback": "A direct, constructive paragraph ...",
    "reasoning": "Explain why these specific strengths ..."
}}

Those doubled braces {{ }} are the f-string escape from section 2 — Python prints them as single braces. So what actually reaches Gemini is clean JSON with placeholder values that double as instructions ("A 3-4 sentence professional summary...").

This technique is called schema-by-example. There is no validation, no type system, no enforcement. You are showing a very capable pattern-matcher an example and trusting it to imitate the shape while replacing the contents. It works remarkably well and is fragile in exactly the way you'd expect: nothing guarantees the model returns those exact key names.

Mechanism 2 — making Google enforce JSON at their end

services/gemini_service.py lines 95–104python
json_prompt = prompt + "\n\nCRITICAL INSTRUCTION: Your entire response MUST be a valid JSON object. Do not include markdown formatting like ```json or any conversational text outside the JSON block."

response = self.client.models.generate_content(
    model=model_name,
    contents=json_prompt,
    config=types.GenerateContentConfig(
        response_mime_type="application/json"
    )
)

Two belts for the same trousers:

  • The appended sentence is more prompt engineering — a plain-English plea, bolted on to every JSON request in one place instead of being repeated inside all four prompts.
  • response_mime_type="application/json" is different in kind. This is a real feature of Google's API called JSON mode / structured output. It doesn't ask nicely; it changes how the model generates text on Google's servers, constraining the output so that it parses as JSON. This is the closest thing to a guarantee in the whole pipeline — and note that it guarantees valid JSON, not the JSON keys you asked for.
Why not go further?

Gemini also supports response_schema, where you hand over a formal schema (or a Python class) and the API guarantees the exact fields and types. This project doesn't use it — instead it draws the shape in the prompt and hopes. That's simpler to write and to read, but it's the reason a mismatched key silently produces a blank section in your dashboard instead of a loud error. See section 10.

This is the only real conversion algorithm in the codebase, and it lives in utils/helpers.py. Its job: take whatever text came back and get a Python dictionary out of it by any means available.

def extract_json_from_text(text: str) -> dict:
    try:
        # First try direct parsing
        return json.loads(text)
    except json.JSONDecodeError:
        pass

    # Try to find JSON block in markdown
    json_match = re.search(r'```json\s*(.*?)\s*```', text, re.DOTALL)
    if json_match:
        try:
            return json.loads(json_match.group(1))
        except json.JSONDecodeError:
            pass

    # Try to find anything that looks like a JSON object or array
    try:
        match = re.search(r'(\{.*\}|\[.*\])', text, re.DOTALL)
        if match:
            return json.loads(match.group(1))
    except Exception:
        pass

    print("Failed to parse JSON from response.")
    return {}

Tier 1 — try it straight

json.loads(text) is Python's built-in JSON parser (part of the standard library, implemented in C for speed). You did not write a parser and you should never need to. If Gemini obeyed response_mime_type, this succeeds on the first try, which it does the vast majority of the time. Note it catches only json.JSONDecodeError — the specific "this text isn't JSON" error. A different failure would still crash, which is correct behaviour: you only want to swallow the error you actually planned for.

Tier 2 — dig it out of a markdown code fence

Language models are trained on a lot of documentation, so their instinct is to wrap code in triple backticks:

a reply tier 1 chokes ontext
Here is the analysis you requested:

```json
{"summary": "Solid fundamentals...", "strengths": ["SQL"]}
```

The regular expression r'```json\s*(.*?)\s*```' reads as: find three backticks followed by the word json, then any whitespace, then capture everything up to the next three backticks. Piece by piece:

r'...'
a "raw string" — backslashes mean themselves, not escape codes. Always used for regex.
\s*
zero or more whitespace characters (spaces, tabs, newlines).
( )
a capture group — the part you want to keep, retrieved later with .group(1).
.*?
any characters, lazily — the ? means stop at the first closing fence rather than the last.
re.DOTALL
normally . refuses to match newlines; this flag lets it, which is essential since JSON spans many lines.

Tier 3 — the brute-force grab

For a reply that has no fence but has chatter around the JSON — "Sure! {"summary": ...} Let me know if you need more." — the pattern r'(\{.*\}|\[.*\])' finds the first { and, because .* here is greedy (no ?), stretches all the way to the last } in the whole text. The | means "or", so it also handles a reply that is a JSON array instead of an object.

Greedy is the right call here: JSON objects contain nested objects, so stopping at the first closing brace would slice the structure in half. The risk is the mirror image — if the model wrote a sentence containing a stray } after the JSON, the grab would include the junk and parsing would fail. Tier 3 is a heuristic, not a guarantee, and that's an acceptable trade for a last resort.

Tier 4 — give up quietly

If all three fail, the function prints a warning to the terminal (not to the browser) and returns {} — an empty dictionary.

The failure mode this creates

An empty dictionary means every later .get('summary', '') in app.py returns its default. The app does not crash — it renders a dashboard with a score of 0/100, empty strength lists, and blank text. To the user this looks like the AI thought they were terrible, when in fact the reply was unparseable. Nothing on screen says "something went wrong". If you improve one thing in this project, make this function raise a clear error (or set a flag app.py can show as a red banner) instead of returning {}.

So which is "the algorithm"?

Put plainly, for your own explanation to anyone who asks:

  1. The prompt converts your intent into text that contains an example of the desired JSON. That's not an algorithm, it's a written instruction.
  2. The Gemini model plus Google's JSON mode converts that instruction into JSON-shaped text. That's a neural network doing constrained token generation on Google's hardware — genuinely the "AI" part, and entirely outside your code.
  3. Your extract_json_from_text converts that text into a Python dictionary using a three-tier fallback: strict parse, markdown-fence extraction, greedy brace extraction. That is the algorithm you own, and it's about twenty lines long.

What does exist #2 — transient vs. permanent error detection

This is the one genuine classifier in the codebase. It classifies errors, not requests.

            print(f"[GeminiClient] {model_name} exhausted retries, falling back to next model...")
            break
    else:
        raise

The logic in plain English:

  1. Take the error, turn it into text, lowercase it.
  2. Check whether any of eight keywords appears in that text. any(... for ...) is a generator expression — read it as "is at least one of these keywords present?"
  3. If yes, this is a transient failure — Google is busy, over quota, or wobbling. Worth retrying.
  4. If no, it's a permanent failure — a malformed request, a bad API key, a safety block. Retrying would fail identically forever, so raise immediately and let the user see it.

The retry maths

wait_time = 5 * (2 ** attempt) is exponential backoff. ** is "to the power of". Attempt 0 waits 5 × 1 = 5s; attempt 1 waits 5 × 2 = 10s. The idea: if a server is overloaded, hammering it immediately makes things worse for everyone; backing off exponentially gives it room to recover. Because max_retries_per_model=2, each model gets two attempts before the chain moves on.

The worst case, calculated

4 models × 2 attempts = 8 total attempts. Only the first attempt per model waits (the second attempt's failure breaks out to the next model), so the waiting adds up to roughly 4 × 5s of backoff plus the mandatory 3s spacing before each of the 8 calls ≈ 45 seconds of pure waiting before the chain gives up and raises "All models in fallback chain failed." Then app.py catches that and shows a red error box.

What does exist #3 — rate-limit spacing

def _wait_for_spacing(self):
    elapsed = time.time() - self._last_call_time
    if elapsed < self.CALL_SPACING:
        time.sleep(self.CALL_SPACING - elapsed)

Before every call, work out how long it's been since the last one. If less than 3 seconds, sleep for the remainder. This is proactive politeness: free-tier Gemini keys have a requests-per-minute cap, and four rapid-fire calls could trip it. The cost is that a full run has at least 9 seconds of deliberate idling baked in.

class GeminiClient:
    """Wrapper for interacting with the Google Gemini API using the new google-genai SDK.

    Uses a model fallback chain to handle 503 'high demand' errors by automatically
    switching to the next available model instead of waiting on an overloaded one.
    """

    MODEL_CHAIN = [
        "gemini-3.7-flash",
        "gemini-3.6-flash",
        "gemini-3.5-flash",
        "gemini-3.5-flash-lite",
    ]

    CALL_SPACING = 3

    def __init__(self):
        api_key = os.getenv("GEMINI_API_KEY")
        if not api_key:
            raise ValueError("GEMINI_API_KEY environment variable not set. Please check your .env file.")

        self.client = genai.Client(api_key=api_key)
        self._last_call_time = 0

    def _wait_for_spacing(self):
        elapsed = time.time() - self._last_call_time
        if elapsed < self.CALL_SPACING:
            time.sleep(self.CALL_SPACING - elapsed)

    def _call_with_fallback(self, make_request, max_retries_per_model=2):
        last_error = None

        for model_name in self.MODEL_CHAIN:
            for attempt in range(max_retries_per_model):
                try:
                    self._wait_for_spacing()
                    self._last_call_time = time.time()
                    return make_request(model_name)
                except Exception as e:
                    last_error = e
                    error_str = str(e).lower()
                    is_transient = any(
                        keyword in error_str
                        for keyword in ["503", "429", "500", "unavailable", "quota", "high demand", "overloaded", "capacity"]
                    )

                    if is_transient:
                        if attempt < max_retries_per_model - 1:
                            wait_time = 5 * (2 ** attempt)
                            print(f"[GeminiClient] {model_name} attempt {attempt+1} failed (transient), retrying in {wait_time}s...")
                            time.sleep(wait_time)
                            continue
                        else:
                            print(f"[GeminiClient] {model_name} exhausted retries, falling back to next model...")
                            break
                    else:
                        raise

        raise Exception(f"All models in fallback chain failed. Last error: {str(last_error)}")

from docx import Document

class ResumeParser:
    """Handles extraction of text from various resume file formats."""

    @staticmethod
    def extract_text(file_obj, filename: str) -> str:
        if not file_obj:
            raise ValueError("No file provided.")

        ext = filename.split('.')[-1].lower()

        try:
            if ext == 'pdf':
                return ResumeParser._extract_from_pdf(file_obj)
            elif ext in ['doc', 'docx']:
                return ResumeParser._extract_from_docx(file_obj)
            else:
                raise ValueError(f"Unsupported file format: {ext}. Please upload PDF or DOCX.")
        except Exception as e:
            raise ValueError(f"Error parsing file: {str(e)}")

    @staticmethod
    def _extract_from_pdf(file_obj) -> str:
        text = ""
        try:
            pdf_reader = PyPDF2.PdfReader(file_obj)
            for page in pdf_reader.pages:
                extracted = page.extract_text()
                if extracted:
                    text += extracted + "\n"
        except Exception as e:
            raise Exception(f"Failed to read PDF: {str(e)}")

        if not text.strip():
            raise Exception("PDF appears to be empty or contains only unextractable images.")

        return text

    @staticmethod
    def _extract_from_docx(file_obj) -> str:
        text = ""
        try:
            doc = Document(file_obj)
            for para in doc.paragraphs:
                text += para.text + "\n"
        except Exception as e:
            raise Exception(f"Failed to read DOCX: {str(e)}")

        if not text.strip():
            raise Exception("Document appears to be empty.")

        return text

Verdict: for a portfolio project that must demonstrate AI capability rather than frontend craft, Streamlit is the correct call by a wide margin. The cost you pay shows up in exactly two places — the re-run model forcing session_state, and CSS selectors that fight Streamlit's internals. Both are visible in your code.

Gemini Flash, instead of GPT / Claude / a local model

  • Gemini's free tier is genuinely usable — for a student project you can run dozens of analyses without a credit card. OpenAI and Anthropic require payment up front for API access.
  • Flash over Pro: flash models are optimised for speed and cost. Four sequential calls on a Pro-tier model would push a run past a minute and cost noticeably more per analysis. For "read this text, produce structured feedback", flash is more than capable.
  • Cloud over local (Llama, Mistral via Ollama): a local model would be free forever and fully private — your resume would never leave the machine. But it needs several GB of RAM, a decent GPU for acceptable speed, quality at small sizes is markedly worse for structured-output tasks, and the setup burden lands on anyone who wants to run your project. For a shareable demo, the API wins.
  • The cost of this choice: your app is only as available as Google's servers. The elaborate fallback chain in gemini_service.py is direct evidence that this bit — the git history shows a commit specifically fixing "API overload" errors.

Prompt-shaped JSON, instead of enforced schemas

You show the model an example and hope. The alternatives, in rising order of strictness:

  1. What you do: example JSON in the prompt + response_mime_type. Valid JSON guaranteed, correct keys not guaranteed.
  2. Gemini's response_schema: hand the API a formal schema; keys and types are enforced by Google. Roughly 10 extra lines per prompt.
  3. Pydantic validation after the fact: define the expected shape as a Python class and validate every reply; a mismatch raises a loud, specific error instead of rendering a blank section.

How the outcome differs: today, a renamed or missed key produces an empty area of the dashboard with no explanation. With either alternative you'd get an immediate, precise error naming the field. For a solo project that's an acceptable trade; for anything with real users it wouldn't be.

Four sequential calls, instead of four parallel ones

Calls 1, 2 and 3 are completely independent — only call 4 (the roadmap) needs call 1's output. Running the first three concurrently with concurrent.futures.ThreadPoolExecutor would cut a 40-second wait to roughly 15.

Why sequential is defensible anyway: three simultaneous requests on a free-tier key are far more likely to trigger 429 rate-limit errors — and the whole CALL_SPACING mechanism exists precisely because that was a real problem. Sequential execution also makes the progress bar meaningful and the code readable top-to-bottom. It's a deliberate speed-for-reliability trade, and worth saying out loud if anyone asks why your app takes 40 seconds.

No caching, no database, no accounts

No cache
Re-analysing the same resume for the same role spends four fresh API calls. A dictionary keyed by a hash of (resume text + role + level) would make repeats instant and free. Roughly 10 lines. The reason it's absent: for a demo, nobody analyses the same resume twice.
No database
Nothing survives a refresh. Adding SQLite would let you track score improvements over time — arguably the single most compelling feature this project doesn't have. It would also mean schema design, migrations and a storage story for resume text, which is real work.
No accounts
With one shared API key and no login, anyone who can reach the URL spends your quota. That's exactly why this should stay a localhost tool until auth exists.

PyPDF2, instead of pdfplumber / PyMuPDF / OCR

PyPDF2 is the most widely known pure-Python PDF reader — easy to install, no system dependencies. pdfplumber extracts text with better layout fidelity and can read tables. PyMuPDF is dramatically faster and more accurate, but ships compiled binaries and carries a restrictive licence. Tesseract OCR would handle scanned resumes but requires installing a separate program outside Python.

Outcome difference: with pdfplumber, multi-column resume layouts (very common in modern templates) would extract in a more sensible reading order. PyPDF2 sometimes interleaves columns into scrambled text — and since that scrambled text is what the AI judges, extraction quality directly caps analysis quality. If you improve one dependency, make it this one.

The one-sentence summary of this project's philosophy

Every decision optimises for getting a working, demonstrable AI product built by one person quickly — and consistently trades away scale, strictness and durability to get there. That is the right optimisation for what this is, and being able to name the trade-offs is what separates "I built it" from "I understand it".
